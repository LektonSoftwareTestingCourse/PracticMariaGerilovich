# Тестовая стратегия СМП

## 1. Цель тестирования

Подтвердить, что СМП корректно проводит платёжную транзакцию по всей процессинговой цепочке:

- цепочка проходит целиком — от приёма транзакции до решения и резервирования средств;
- авторизация корректна: валидные операции принимаются, невалидные отклоняются;
- `responseCode` соответствует реальной причине отказа;
- для каждого статуса карты и причины отказа выдаётся корректный ответ.

Приоритет — корректность бизнес-логики и денежных значений, а не отображение в интерфейсе.

## 2. Объект тестирования

Объект тестирования - система медленных платежей в целом, состоящая из следующих сервисов:

| Сервис | Роль в системе |
|---|---|
| Authorization | «мозг» процессинга: принимает решение APPROVED/DECLINED, проверяет карту, лимиты, баланс, резервирует средства |
| Card Management | источник данных о картах: CRUD, генератор тестовых карт, статусная модель, резервирование средств |
| Gateway | точка входа внешних запросов |
| Switch | маршрутизация транзакций между сервисами |
| Terminal Simulator | эмуляция работы терминала, отправка транзакций |
| Merchant Simulator | эмуляция работы мерчанта |
| Transaction Logger | фиксация и хранение журнала транзакций |
| Bin Lookup | обогащение данных эмитента по BIN |
| Notification Service | асинхронное уведомление о событиях карт |
| Web Dashboard | отображение состояния системы |

## 3. Уровни тестирования

Применяются следующие уровни проверок:

- Дымовое (smoke)
- Модульное (unit)
- Интеграционное
- Системное (E2E)

## 4. Область тестирования

### 4.1. Что входит в область

Тестированию подлежит **вся СМП**, однако глубина проверок распределена риск-ориентированно:

- **ядро системы** (Authorization, Card Management) - тестируется глубоко: полный тест-дизайн по технике классов эквивалентности, граничных значений и попарного тестирования;
- **периферийные сервисы** (Gateway, Switch, симуляторы, Transaction Logger, Web Dashboard) — проверяются на верхнем уровне: дымовое тестирование и проверка критического пути.

### 4.2. Что осознанно не входит в область и почему

Следующие виды проверок **осознанно исключаются** из области тестирования на данном этапе:

| Исключено                                           | Основание                                                                                                                                                      |
|-----------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Нагрузочное тестирование**                        | требует отдельной нагрузочной среды и инфраструктуры                                                                                                           |
| **Тестирование безопасности**                       | требует отдельной методики и инструментов                                                                                                                      |
| **Верификация держателя карты** (PIN, CVV)          | реализуется стабами (всегда принимают `1234`/`123`), реальные данные не используются                                                                           |
| **Общая отказоустойчивость**                        | требует отдельной инфраструктуры и выходит за рамки артефакта                                                                                                  |
| **Глубокая работа с брокером сообщений** (RabbitMQ) | асинхронный обмен (outbox-события Card Management → Notification Service) тестируется на уровне интеграции, глубокий анализ самого брокера не входит в область |
| **Внешний вид Web Dashboard (UI)**                  | проверки отображения имеют низкий приоритет по сравнению с проверками бизнес-логики                                                                            |

Исключение перечисленных областей позволяет сконцентрировать ограниченные ресурсы тестировщиков на проверках, связанных с финансовыми последствиями, и уложиться в сроки проекта.

## 5. Риск-ориентированный подход

### 5.1. Принципы приоритизации

Приоритет проверок определяется величиной финансовых и операционных последствий отказа:

1. в первую очередь тестируются сценарии отказа с финансовыми последствиями: **превышение лимита**, **недостаток средств**, **повторное резервирование средств** — вендор системы несёт прямые потери;
2. проверки денежных значений выполняются **до** проверок, связанных с отображением в интерфейсе;
3. внешний вид и оформление интерфейса не являются приоритетом тестирования;
4. ядро системы (Authorization, Card Management) получает глубокий анализ требований и соответствующее по объёму тестирование; периферийные сервисы — только критический минимум.

### 5.2. Следствие

Осознанный отказ от глубокого тестирования периферийных сервисов является **принятым проектным риском**: возможные дефекты в их логике признаются допустимыми на данном этапе ради концентрации усилий на ядре. Такой подход соответствует риск-ориентированному тестированию, при котором объём работ следует за риском.
