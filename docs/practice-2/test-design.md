# Test-design ядра: Authorization и Card-Management

## 1. Классы эквивалентности

### 1.1. Authorization

Классы выделены по полям авторизационного запроса и данным карты. Позитивные и негативные классы выделяются раздельно; один невалидный класс — один тест-кейс.

| Поле | Позитивные классы | Негативные классы |
|---|---|---|
| `card_status` | ACTIVE | INACTIVE, BLOCKED, EXPIRED |
| `amount_vs_daily` | amount < dailyLimit, amount = dailyLimit | amount > dailyLimit |
| `amount_vs_monthly` | amount < monthlyLimit, amount = monthlyLimit | amount > monthlyLimit |
| `amount_vs_balance` | amount < availableBalance, amount = availableBalance | amount > availableBalance |
| `expiry` | valid (будущий MMYY), current_month (текущий MMYY) | expired (MMYY < текущего) |
| `terminal_type` | pos, atm, ecom | — (все значения из списка валидны) |
| `mcc` | grocery, restaurant, electronics, travel | — (все значения из списка валидны) |

### 1.2. Card-Management

Классы выделены по операциям CRUD и данным карты.

| Поле | Позитивные классы | Негативные классы |
|---|---|---|
| `operation` | create, read, list, update, delete, reserve, generate | — |
| `pan_format` | valid_luhn (проходит алгоритм Луна) | invalid_luhn, not_found |
| `card_status` | ACTIVE, INACTIVE, BLOCKED, EXPIRED | — |
| `expiry_format` | valid (будущий MMYY) | expired |
| `bin` | known (6 цифр, есть в таблице) | unknown (нет в таблице → `BinNotFoundException`) |
| `reserve_balance` | sufficient (средств хватает), exact | insufficient (недостаточно) |

## 2. Граничные значения (BVA)

Для каждой границы берутся три точки: ON (на границе), OFF (сразу за границей), + значение внутри класса.

### 2.1. Authorization

| Поле | ON | OFF | Ожидаемый результат |
|---|---|---|---|
| `dailyLimit` | amount = dailyLimit | amount = dailyLimit + 1 | ON → APPROVED (00); OFF → DECLINED (61) |
| `monthlyLimit` | amount = monthlyLimit | amount = monthlyLimit + 1 | ON → APPROVED (00); OFF → DECLINED (61) |
| `availableBalance` | amount = availableBalance | amount = availableBalance + 1 | ON → APPROVED (00); OFF → DECLINED (51) |
| `expiryDate` (MMYY) | expiryDate = текущий месяц | expiryDate = предыдущий месяц | ON → APPROVED (00); OFF → DECLINED (54) |


### 2.2. Card-Management

| Поле | ON | OFF | Ожидаемый результат |
|---|---|---|---|
| `bin` | 6 цифр | 5 / 7 цифр | ON → BIN валиден (проверка `@Bin`); OFF → ошибка валидации (400) |
| `expiryDate` (MMYY) | expiryDate = текущий месяц | expiryDate = предыдущий месяц | ON → срок валиден; OFF → срок истёк (сценарии EXPIRED) |
| `reserve_balance` | amount = availableBalance | amount = availableBalance + 1 | ON → резервирование успешно (баланс = 0); OFF → 402 `InsufficientFundsException` |

## 3. Попарное тестирование (pairwise)

Попарное тестирование построено инструментом **PICT**. Для каждого сервиса ядра задана модель с параметрами и ограничениями, сгенерирован набор, покрывающий все пары значений.

### 3.1. Модель Authorization (`pict/model_auth`)

Ограничения исключают невозможные сочетания: при не-ACTIVE карте лимиты и баланс не проверяются (карта отклоняется по статусу раньше); при истёкшем сроке баланс не проверяется. Полный перебор — 4×3×3×3×3×3×4 = 3888 комбинаций, попарный набор — **25 строк** (`cases_auth`).

### 3.2. Модель Card-Management (`pict/model_cm`)

Ограничения исключают невозможные сочетания: при создании карты PAN всегда корректен, срок не истёк, статус ACTIVE (сервер генерирует PAN и срок); при генерации PAN корректен, срок valid, статус не EXPIRED (generate создаёт только ACTIVE/INACTIVE/BLOCKED); `reserve_balance` значим только для `reserve`. Попарный набор — **30 строк** (`cases_cm`).

**TC-AUTH-01** — позитивный: авторизация активной карты
- **Требование**: `04-authorization.md`, алгоритм авторизации
- **Вид**: позитивный
- **Предусловие**:
  - карта заведена в системе, `availableBalance` = 1000.00 ₽
  - `dailyLimit` = 10 000.00 ₽, `monthlyLimit` = 300 000.00 ₽
  - карта ACTIVE, срок действия валиден
  - по карте операций не было (новая, чтобы не попасть в дневные/месячные лимиты)
- **Вход**: статус карты = ACTIVE, сумма транзакции = 900.03 ₽, терминал = pos, mcc = grocery
- **Шаги**: провести транзакцию на 900.03 ₽
- **Ожидаемый результат**:
  1. Операция успешна: APPROVED, `responseCode="00"`
  2. Средства зарезервированы; `availableBalance` уменьшился на 900.03 ₽ → 99.97 ₽
  3. Дневной usage увеличился на 900.03 ₽; месячный usage увеличился на 900.03 ₽
  4. Сгенерированы RRN (12 цифр) и authCode (6 символов)
- **Источник**: КЭ (`card_status` = ACTIVE)
